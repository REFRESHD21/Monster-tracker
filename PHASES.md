# Upgrade progress

## Phase 1 — built and verified

- Database version 1/2 → 3 adds tables and triggers; it does not rebuild, reset, rename or alter the existing ledger, settings, pending commands, opening IDs or dates.
- Existing ledger rows are backfilled into an append-only audit. New ledger rows are audited by a SQL trigger in the same transaction, including the original undo behavior.
- Offline supplier purchases have reviewed supplier/reference/date, multiple lines, multipacks, gross line costs, actual GST shown, notes and original JPG/PNG/PDF attachments. The date can explicitly remain unknown.
- Receipts can be imported or photographed. Original bytes are retained in private SQLite, immutable, and SHA-256 fingerprinted. A receipt already linked to a saved document or a repeated supplier/reference is rejected instead of creating another purchase.
- Document confirmation does **not** add stock. A separate goods-received confirmation supports partial deliveries. Quantity and cumulative cost allocation are checked inside the same transaction as the restock and delivery/audit rows; repeated delivery IDs are idempotent.
- Operating expenses and mixed purchase expense lines are recorded without changing stock. Expense undo/cancellation appends a correction; no saved row is edited/deleted. Cancelling a purchase stops additional delivery confirmations, while existing deliveries remain explicit ledger records and can be undone through History.
- Dashboard retains the existing cash result after stock and adds expenses/result after stock and expenses. Purchase invoice totals are retained separately; this phase is not a profit/COGS or BAS report. Received stock carries allocated gross cost; unreceived costs are not yet part of the legacy inventory cash-result calculation.
- Version-3 full JSON backup includes documents, receipts (original bytes), deliveries, corrections and audit history. Version-1 and version-2 backups remain readable and merge without clearing the newer domain. Files and receipts have size limits (64 MB full JSON, 16 MB each receipt); oversized exports fail visibly instead of writing a truncated file.
- Privacy: receipts stay app-private; selected originals may be opened in an installed offline viewer via a narrow read-only URI grant. No database URI or additional network permission was added; Phase 2 requests camera access only for capture/scanning. Existing Stripe/network setup from main is preserved.

## Phase 3 — built and verified

- Version 5 adds immutable historical GST snapshots and future-only audited tax settings. No event, receipt, purchase or stock table is rebuilt. Existing history defaults to unregistered/no inferred credits; GST registration defaults OFF.
- FIFO inventory valuation uses immutable ledger insertion order (not backdated sale dates), cents-exact remaining lot costs and flavour transfers. Transfers now retain their ledger anchor so same-millisecond activity and restored opening ingestion times do not change cost ordering. Existing version-4 transfers remain readable.
- Later stock purchases and settings changes do not reprice earlier sales. Undo returns the original consumed costs; undo of a consumed restock withdraws available stock and shows any valuation difference as an explicit correction loss/gain. Existing undo remains supported.
- Reports show gross revenue, cash/card, actual recorded fees, COGS, gross profit, operating expenses, missing/damaged/lost stock valuation, estimated net profit, GST estimates and current inventory value. Flavour gross profit excludes shared fees/expenses. Daily, weekly, monthly, quarterly, calendar-year, Australian financial-year and all-history filters use Perth time. Input-taxed inventory does not receive a credit.

## Phase 4 — built and verified

- Portable AES-256-GCM encryption uses a random salt/nonce for every backup and PBKDF2-HMAC-SHA256 (310,000 iterations). The entire header is authenticated. Passwords are required, confirmed for exports and never embedded in APK/source/backup metadata. Wrong passwords, malformed lengths, altered work factors, tampering and invalid decrypted JSON are rejected before restore.
- Full encrypted backups preserve all version-5 business records/settings, original receipts, inventory, audit/corrections and financial snapshots. Export writes and reads back/decrypts the selected file. Restore previews new event counts and explicitly confirms merging records/restoring future settings; matching IDs are skipped and conflicts roll back atomically. Existing ordinary JSON/CSV options remain.
- Scheduled daily/weekly local backups use Android JobScheduler and persist across reboot. The schedule defaults OFF. Its password is encrypted using Android Keystore, but portable backup decryption uses the user password so a replacement phone does not need the old device key. Password changes do not change older backups.
- Automatic/manual recovery copies use a transactional SQLite snapshot, a private partial file, fsync, decrypt/readback validation and atomic rename. The latest seven finalized local copies are retained; originals and live records are not deleted. Interrupted temporary files are not presented as recovery copies.
- An optional Android Storage Access Framework folder can receive verified encrypted copies. This may be local removable storage or a provider offering cloud sync; the app does not implement a paid cloud service/account. Actual remote cloud durability is provider-dependent and unverified. A provider failure retains the verified local recovery copy and reports the failure. Provider copies are not automatically deleted.
- Uninstall/clear-data/phone loss also removes private recovery copies and device-keystore secrets. Keep a portable encrypted file and its password outside the phone. Scheduled-backup secrets, Stripe pairing credentials and device permission state are excluded intentionally and must be configured again on a replacement device. Android scheduling may be delayed by idle/battery restrictions; Back up now creates/verifies the first copy.
- Eight host encryption checks and four Android checks cover encrypted complete receipt restore, Keystore wrapping/job configuration, atomic local recovery/readback and wrong-password database protection (36 offline Android checks in total). Physical folder-provider/cloud synchronization and real background timing need device verification.

## Phase 5 — built and verified; actual Stripe credentials/hardware unavailable

- Current official Stripe documentation was checked on 2026-10-13: Tap to Pay on Android is available in Australia (including eftpos); the documented SDK dependencies are 6.0.0. Requirements include supported NFC/ARM hardware, Android 13+, recent security patches, a locked unmodified device and the documented Google/device conditions. The existing native SDK flow is retained. No offline card processing is enabled or claimed.
- The authenticated HTTPS backend retains durable payment/refund IDs and separate test/live databases. Live mode still requires both an explicitly enabled live backend and phone configuration. Secret keys remain only in server environment variables; phone pairing credentials remain Keystore-encrypted. No credential or real charge has been configured during this work.
- The existing SDK checks a saved checkout with the server before processing/canceling. Background connected-network recovery now checks only `/status` for an already pending checkout; it never creates or processes a charge. Successful live sales finalize exactly once when their actual settlement fee is known; unknown fees leave a visible pending checkout and retry safely. SDK/background finalization shares validation/idempotency and immutable flavour/tax plans. Only that payment's cans are reserved while its fee is unresolved. Other available stock remains usable for offline cash/manual sales and adjustments; physical counts of a reserved flavour wait to avoid counting handed-over cans twice.
- Durable authenticated `/refund`, `/refund_status` and `/reconcile` endpoints create/retrieve one Stripe refund per request UUID. They verify original sale, AUD amount, mode, provider ID/status/timestamps and actual additional fees. Retries/concurrent taps/lost responses/restarts reuse the same refund. Uncertain creations freeze before idempotency retention expires; reconciliation adopts matching provider metadata and imported Dashboard refunds. No webhook endpoint is assumed; status reconciliation uses authenticated server-side Stripe retrieval and explicit/background payment status checks.
- SQLite version 6 adds immutable refund requests, status observations and returned-goods confirmations with safe migrations and append-only audit. Manual cash/card refunds work offline; original sales and original processing fees remain. Only successful verified/recorded refunds reduce net revenue. Later verified failures append financial reversals; observed dates are labelled as verification dates. Pending/failed/canceled requests remain traceable. Unknown additional refund fees are explicitly marked/excluded until verified.
- Returned cans are never automatically added by a refund. A separate physical receipt creates one source-linked stock return, restores original FIFO cost and reverses the returned COGS without treating it as a purchase. Over-refunds/over-returns, conflicting IDs, stale observations and undo of a refund-linked source sale are rejected atomically. Other undo behavior remains, including undoing mistaken goods receipts.
- Dashboard/report cash/card/net revenue/results include refund effects; gross sales/deals remain visible. CSV/PDF financial reports include refunds, fee changes, reversals and stock returns. Full JSON/encrypted backups include all refund links/history and reject conflicts.

Running it requires the owner's configured Stripe test backend and compatible physical phone. Neither actual SDK payment collection nor a real Stripe API test write/readback has been performed here.

## Monster Business intelligence upgrade — staged implementation

The active target is `universal/` (Flutter), branch `feature/flutter-universal-tracker`, commit `d775056` at inspection. The root Java app remains the migration/accounting reference. See [BI_IMPLEMENTATION_PLAN.md](BI_IMPLEMENTATION_PLAN.md) for the inspected data model, dependencies, external blockers, and phased sequence.

### Phase 1 — purchase history and sales/profit foundation (working tree)

- The existing integer-cent, append-only event ledger and FIFO inventory remain the source of truth. Each new multi-product purchase is stored as grouped, immutable costed restock events; retailer observations are explicitly separate.
- Purchase entry captures supplier, store location, reference, purchase date (including unknown), multiple products, 4/9/12/24/custom pack quantity, pack count, item cost, discount, allocable acquisition cost, actual eligible GST, and notes. Purchase receipt events commit together through one state save and repeated purchase IDs are idempotent; conflicting resubmissions are rejected.
- Purchase history groups new receipt events and shows older standalone restock records without inventing missing supplier or pack facts. Full backups serialize these event details; the one-way Sheets Purchases tab includes the purchase fields.
- Added purchase-cost, FIFO reconciliation, backup roundtrip, invalid-link and duplicate-submission tests. Existing sales/profit, refunds, returns, damaged-stock treatment, and net-profit functions remain in place.
- This phase has not passed the Flutter test/build workflow. The bundled Dart VM aborts in this workspace before running `dart format` or Flutter tests; the legacy Java/SQLite and Sheets suites remain runnable and passed.
